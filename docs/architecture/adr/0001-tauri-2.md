# ADR 0001 — Tauri 2 + Rust core + Tauri Mobile

- **Status**: Accepted
- **Date**: 2026-05-25
- **Deciders**: Owner del prodotto + Claude (sessione iniziale di pianificazione)

## Contesto

Medea deve essere distribuita come applicazione standalone su tre piattaforme: **Windows** (`.exe`), **macOS** (`.dmg`) e **Android** (`.apk`). Il materiale di partenza per la logica email (IMAP/SMTP/Gmail/OAuth/DB) vive in JavaScript dentro `nha-toolkit/src/services/*.mjs`. L'app esistente `NotHumanAllowed/apps/3rdarm-desktop` è un wrapper Electron che lancia un server Node locale e mostra una BrowserWindow puntata su `localhost:3847`.

Bisogna scegliere il runtime di Medea e di conseguenza:

1. dove vive la logica mail (Node sidecar? Rust nativo?),
2. come si arriva ad Android in modo coerente con il desktop,
3. come distribuiamo binari firmati e aggiornati nel tempo.

## Opzioni considerate

### A) Electron 33 + Capacitor 7 (status quo evoluto)

- ✅ Riusa il codice `.mjs` esistente al 100%, time-to-MVP ridotto.
- ❌ Bundle ~250MB, RAM ~400MB a vuoto.
- ❌ Capacitor mobile = secondo binario logico, sync stato fra desktop e mobile diventa un problema reale.
- ❌ Sandbox/capability scarse, sicurezza affidata al rigore dell'app.
- ❌ Non «alza lo standard tecnologico» — è la stessa cosa che fa già `3rdarm-desktop`.

### B) Tauri 2 + sidecar Node (compromesso)

- ✅ Bundle desktop ~15MB.
- ✅ Sicurezza granulare via capabilities.
- ⚠️ Mobile NON funziona — Node non gira come sidecar su Android.
- ⚠️ Doppia distribuzione di runtime (Rust + Node bundled) complica firma e aggiornamenti.

### C) Tauri 2 + core Rust nativo subito

- ✅ Bundle ~15MB, RAM ~80MB.
- ✅ Stesso binario logico su desktop e mobile (Tauri 2 Mobile usa la stessa codebase Rust + WebView).
- ✅ Sicurezza memory-safe, capabilities granulari, niente IPC con processi figli.
- ✅ Crate Rust per IMAP (`async-imap`), SMTP (`lettre`), DB (`rusqlite`), HTTP (`reqwest`), crypto (`aes-gcm`, `keyring`) sono maturi nel 2026.
- ❌ Richiede porting del materiale JavaScript in Rust — costo iniziale di 1-2 mesi di lavoro core prima di vedere parità funzionale.

## Decisione

**Opzione C — Tauri 2 + core Rust nativo subito + Tauri 2 Mobile per Android.**

Il porting JS→Rust è costoso ma è investimento, non spreco: il sync engine (vedi [ADR 0002](./0002-sync-engine-is-the-product.md)) richiede comunque garanzie di correttezza e performance che il prototipo Node non offre, e Android richiede comunque il porting perché Node non gira come sidecar. Spalmare il porting su 2 fasi diverse (prima Node sidecar, poi Rust per mobile) significherebbe pagare il costo due volte.

## Conseguenze

### Positive

- Un solo binario logico desktop+mobile.
- Bundle e RAM dimensionati per essere distribuiti anche su hardware modesto.
- Sicurezza built-in via Tauri capabilities + memory-safe Rust.
- Dipendenze runtime zero lato utente (niente Node installato, niente Java per Android — solo Tauri).

### Negative

- Porting JS→Rust del mail core costa 3-4 settimane (Fase 1) + sync engine 4-5 settimane (Fase 2).
- Curva di apprendimento Rust per chiunque venga da un mondo solo-JS.
- Cross-build limitato: `.dmg` richiede runner macOS, `.exe` richiede runner Windows, `.apk` richiede NDK su Linux. La CI matrix è obbligatoria.

### Vincoli operativi

- Niente compile-time DB check (`sqlx`) — rompe la CI cross-platform. Usiamo `rusqlite` con `spawn_blocking`.
- Niente PGlite per il vector store — gira solo in WASM, incompatibile con `aarch64-linux-android`. Usiamo `sqlite-vec` come extension caricata.
- Niente sidecar Node «per riusare un po' di JS». Se serve davvero (es. una libreria che non esiste in Rust), si valuta caso per caso ma resta un'eccezione, non un pattern.
